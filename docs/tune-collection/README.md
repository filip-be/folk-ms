# Tune Collection

An Organization that holds sessions keeps a Tune Collection: a catalogue of the Tunes played there, with their Other Names, Tune Type, Key, Time Signature, Transcription in ABC, Recordings, Attachments and Sets. Moderators manage it in the admin SPA; the CMS publishes it as two kinds of per-Site snapshot, a catalogue and one file per Tune, which the Site shows as sheet music that plays. It is opt-in per Organization; only Celtycki Wrocław has it. It uses the CMS, the admin SPA, Storage, the contract, the Sites and abcjs, the one runtime npm dependency ([ADR 0012](../architecture/adr/0012-abcjs-and-self-hosted-samples.md)). It follows the [Video Collection](../video-collection/README.md), with the differences noted below.

## How it works

- **Opt-in.** An Organization has a Tune Collection only when its Site in [`config/sites.json`](../../config/sites.json) has a `tunes` block with the Tune and Set Permalink templates (`/{lang}/tunes/{shortId}-{slug}`, `/{lang}/sets/{shortId}-{slug}`). For any other Organization every `/api/orgs/<org>/tunes…` route answers 404, the admin shows no Tunes section and no tunes snapshot is written.
- **One document per Organization**, `orgs/<org>/tunes.json` in the private store: Tune Types, Instruments, Origins, Tunes and Sets. One document keeps the "in use" checks and taking a removed Tune out of its Sets atomic. Limits: 1000 Tunes, 500 Sets, 50 Tune Types, 100 Instruments, 10 Other Names, Recordings and Attachments per Tune, ABC up to 16 KB, a description up to 10 000 characters per language. Ids are 8-character base32 and never reused.
- **Per-item revisions** (unlike the Video Collection's one version): every Tune, Set and list entry carries its own revision, which a change sends in `If-Match`. The CMS loads the latest document, applies the change if that item is still at the revision sent, and saves with the document's ETag, rerunning the change on a concurrent save (up to 8 times). A change is refused with a conflict only when the same item changed meanwhile, so a long ABC or description edit is not lost to another Moderator's change elsewhere or to an import. Hide and Show carry no revision; an import only creates Tunes and never conflicts.
- **A collection never saved reads as seeded**: the common Irish Tune Types (each with a default Time Signature and Playback Tempo) and the session Instruments, with fixed ids, so a screen can refer to them before anything is saved; the first change creates the document. Its snapshot therefore lists the seeded lists and no Tunes.
- **Access and Audit Log** as for Videos: the Organization's Moderators and the Super Admin; actions `tune.*` (including `tune.attachment.*`), `tuneset.*`, `tunetype.*`, `instrument.*` and `tuneorigin.*` (apart from the Video Collection's `origin.*`). A removed Tune keeps its name there.
- **Languages:** a description, an Attachment caption, a Set name or a translation may be written in either language first; a Site shows the other where one is missing. A Tune Type, Instrument or Origin label needs at least one language.
- **Transcription and Incipit.** A Go ABC reader (`abc.go`) parses the header and proposes the Key (first `K:`) and Time Signature (`M:`, `C` → 4/4, `C|` → 2/2); the Moderator decides. It counts bars (repeats, endings, inline fields, comments, decorations, chords, grace notes) and note lengths from `L:`/`M:` to treat a short first bar as a pickup, and derives the Incipit: the header, the pickup and the first 2 bars, or 1 to 8 as the Moderator chooses. The admin asks `POST …/tunes/abc-preview` while the Moderator types, so one parser decides.
- **Why a Go ABC reader beside abcjs.** abcjs only draws and plays, in the browser. What the CMS publishes or proposes is decided on the server: the Incipit in the catalogue snapshot, the Key and Time Signature proposals, and splitting a multi-tune import at `X:`. The CMS is stdlib-only Go ([ADR 0003](../architecture/adr/0003-stdlib-only-go.md)) and runs no JavaScript, so it reads the ABC itself, and the admin's preview of those values asks the same reader: what the Moderator sees is what is published.
- **Description** is a Markdown subset (paragraphs, line breaks, bold, italic, `https:`/`mailto:` links with `rel="nofollow noopener ugc"`, lists, `#`/`##` headings as `h3`/`h4`, block quotes) rendered to HTML **by the CMS** (`markdown.go`): every character is escaped, raw HTML never passes, and the output uses only the renderer's own tags, without classes or styles. The admin previews with the same renderer (`POST …/tunes/markdown-preview`); the snapshot carries the HTML and Sites style plain tags.
- **Recordings:** YouTube and Vimeo links are parsed by the Video Collection's link parser (start time kept, Vimeo checked with oEmbed and given a thumbnail) and play on the Site; any other `https:` link is kept as a link showing its host (`POST …/tunes/link-preview`).
- **Attachments** are images (JPEG, PNG, WebP: decoded with the image limits and re-encoded to JPEG at 480, 960 and 1600 px, which strips metadata) or PDFs (first bytes `%PDF-`, up to 15 MB, kept as uploaded), up to 10 per Tune. They are stored **per Tune**, never shared between Tunes, at `pub/media/<org>/tunes/<tuneId>/<hash>.pdf` or `<hash>-<width>.jpg`, with a fixed `Content-Type` and `Content-Disposition: inline; filename="…"`. Removing an Attachment or its Tune deletes the files after the document is saved; a failed delete leaves an orphan, which is logged.
- **No `nosniff` on Attachments.** The `pub` container is served by Storage directly, which cannot add `X-Content-Type-Options` (the local `/pub/` does). The mitigations: images are re-encoded, PDFs must start with `%PDF-`, the `Content-Type` is fixed by the CMS, and the files are served from the storage origin, never the Site's or the admin's.
- **Sets** have 2 to 10 Tunes in order and an optional name (otherwise the Tunes' names joined with " / "). Removing a Tune that is in Sets needs `?confirm=true` (409 `needs_confirmation` without, naming the Sets); it is taken out of them in the same write, and a Set left empty is removed. A Hidden Tune stays in its Sets but is left out on the Site; a Set with fewer than 2 visible Tunes is not published.
- **Import:** `POST …/tunes/import-preview` splits a multi-tune ABC file (up to 1 MB) at `X:` and proposes each tune's fields from `T:`, `R:`, `K:`, `M:`, `O:` and `C:`, flagging duplicate names; `POST …/tunes/import` creates the ticked ones, Hidden, in one write.
- **Snapshots** ([`contract/README.md`](../../contract/README.md)), each with its own schema at `schemaVersion` 1:
  - the **catalogue** `pub/sites/<site>/tunes.json`: the lists, every visible Tune in catalogue order (by name, ignoring a leading "The", "An", "A" or "Na" and diacritics) with its Incipit, first Recording and `rev`, and the published Sets with their visible Tune ids;
  - one **Tune file** `pub/sites/<site>/tunes/<id>.json` per visible Tune: the Transcription, the description HTML, Recordings with `url`/`embedUrl`/`thumbnail`, Attachments with URLs, sizes and captions, and the Sets it is in. Its `rev` in the catalogue is a hash of the file's content; the Site adds it to the file's address to bypass caches.
- **Rebuild** (after every change, at every CMS start and on `POST /api/admin/rebuild`): read the published catalogue (one GET; missing or unreadable counts as empty), write the Tune files that are new or whose `rev` changed, delete the files of Tunes in the old catalogue but not the new one and of every Hidden or removed Tune the document knows (`removedTunes`; an older rebuild on another instance may have rewritten one), and write the catalogue **last**, with ETag compare-and-swap. If a file write or delete fails, the catalogue is not written, so the next rebuild tries again. An unchanged start costs one GET and one catalogue write.
- **Reader:** `contract/client/src/tunes.ts` loads the catalogue and a Tune file and offers search over every name and translation (case- and diacritics-insensitive), filters by Tune Type, Key (tonic and/or mode), Origin (a country includes its regions) and Instrument (Suits, or not Tricky on), grouping by Key, Tune Type or Origin, sorting, language fallback, Permalinks, player addresses and the tempo line for playback.
- **Site pages** (`sites/shared/tunes.ts`, only Celtycki Wrocław): `/<lang>/tunes` (search, filters and Group by in the query string, each row's Incipit drawn when it scrolls into view with a play button, ticked Tunes printed together), `/<lang>/tunes/<id>-<slug>` (sheet, playback with sound and tempo, details, description, click-to-load Recordings, images and inline PDFs with an "Open PDF" card, Sets, Share, Print) and `/<lang>/sets/<id>-<slug>`. Printing uses the browser's "Save as PDF"; there is no PDF library. Details in [`sites/README.md`](../../sites/README.md).
- **abcjs and samples:** abcjs is installed from npm at an exact version, updated by Dependabot ([ADR 0012](../architecture/adr/0012-abcjs-and-self-hosted-samples.md)). `notation/abcjs.ts`, shared by the admin and the Sites, `import()`s its prebuilt `dist/abcjs-basic-min.js`, so it is its own chunk (`chunks/abcjs-basic-min-<hash>.js`) that only Tune screens and pages load. The samples are vendored: the instrument samples (piano, flute, fiddle, accordion, from FluidR3 GM by Frank Wen, CC BY 3.0) are served from the Site's own origin under `/sounds/`; the admin preview plays piano only, under `/app/sounds/`. Wherever samples play, the page shows the CC BY credit (`SOUNDFONT_CREDIT`).
- **CSPs.** abcjs inserts `<style>` elements and `style` attributes, so the admin and the Wrocław Site allow `style-src 'self' 'unsafe-inline'`; scripts stay `'self'`. The Site's `frame-src` allows the two embed hosts and the public storage origin (inline PDFs), which is also in `img-src` and `connect-src`. The storage origin is known only at deploy time: the Site's `staticwebapp.config.json` names it `{{STORAGE_ORIGIN}}`, and `sites/build.ts` fills in the origin of `SNAPSHOT_URL` (`vars.STORAGE_PUBLIC_URL` in `deploy-site.yml`, the local CMS otherwise).

## Change together

| Rule | Files | What breaks |
| --- | --- | --- |
| The schemas, the Go builder, the reader and the Site module describe the same `tunes.json` and `tunes/<id>.json`, at the same `schemaVersion` | `contract/tunes.schema.json`, `contract/tune.schema.json`, `contract/fixtures/tunes/`, `contract/fixtures/tune/`, `cms/internal/domain/tune_snapshot.go` (`TuneSnapshotSchemaVersion`), `contract/client/src/tunes.ts` (`TUNES_SCHEMA_VERSION`), `sites/shared/tunes.ts` | Sites fail to read or misread Tunes. Enforced in CI: `cms/internal/schema` validates the fixtures, `cms/internal/domain/tune_schema_test.go` validates built snapshots, `contract/client/test/tunes.test.ts` reads the fixtures. |
| The Site's CSP `frame-src` allows exactly the embed hosts and the storage origin, and `{{STORAGE_ORIGIN}}` is filled at build | `sites/celtycki-wroclaw/staticwebapp.config.json`, `sites/swa-config.ts`, `sites/build.ts`, `cms/internal/domain/video.go` (`EmbedURL`), `contract/client/src/tunes.ts` (`EMBED_HOSTS`, `THUMBNAIL_HOSTS`), `deploy-site.yml` (`SNAPSHOT_URL`) | Players or inline PDFs stay blank, or Attachment images do not load. Enforced by `sites/shared/tunes.test.ts` (built CSP). |
| The admin and Site CSPs allow what abcjs and the samples need: `style-src 'unsafe-inline'`, samples from `'self'` | `cms/internal/http/server.go` (`securityHeaders`), `cms/internal/http/static.go` (`.mp3` type), `cms/admin/build.ts` (copies piano to `/app/sounds/`), `sites/<site>/staticwebapp.config.json` (`navigationFallback.exclude` of `/chunks/*`, `/sounds/*`), `notation/abcjs.ts` (`synthOptions`) | Sheets draw unstyled or playback is silent. `cms/internal/http/tunes_test.go` checks the admin CSP and the sample type, `sites/shared/tunes.test.ts` the Site's. |
| A Tune Collection problem path has a matching `data-field` | `cms/internal/domain/tune.go` (`name.name`, `otherNames.<i>.…`, `typeId`, `key`, `meter`, `tempo`, `abc`, `incipitBars`, `recordings.<i>.…`, `description.<lang>`, `tuneIds`, `label.pl`, …), `cms/internal/app/tunes.go` (`file`, `description`, `abc`), `cms/admin/src/views/tune*.ts` | The problem shows only in the summary (see [Design system, Change together](../design-system/README.md#change-together)). |
| abcjs is the only runtime npm dependency, at an exact version locked with integrity, and only `notation/abcjs.ts` imports it, through `import()` of the dist file; the samples match their `SHA256SUMS` | `package.json`, `package-lock.json`, `notation/abcjs.ts` (`import()`), `vendor/soundfonts/FluidR3_GM/`, `scripts/samples.ts`, `scripts/vendor.test.ts` | Other dependencies slip in, abcjs lands in `app.js` / `main.js` and every screen and page downloads it, or unreviewed samples ship. | A Site with `tunes` in `config/sites.json` routes its Permalink templates to the Tune and Set pages, and gets the samples | `config/sites.json` (`tunes`), `cms/internal/config/`, `sites/shared/tunes.ts` (`matchTunes`), `sites/<site>/src/main.ts`, `sites/build.ts` (copies `/sounds/`) | "View on Site" and shared links lead to the Events fallback, or playback is silent.
